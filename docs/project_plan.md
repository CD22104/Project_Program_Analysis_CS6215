## 2 研究问题和范围

**RQ1 准确性。** 与原始符号基线和不使用 LLM 的参数敏感版本相比，摘要辅助分析在预处理泄漏检测上有哪些收益与退化？

**RQ2 核验作用。** 对同一批模型摘要，证据检查能否减少错误的安全判断、虚构依赖和错误调用点匹配？核验会牺牲多少覆盖率？

**RQ3 稳健性和成本。** 语义保持的重命名、函数封装及无关注释是否改变结果？重复运行是否稳定，代价是多少？

最低实现范围为二维表格数据、行表示样本、列表示特征；单文件 Python 程序或按保存顺序导出的 Notebook；静态可解析的普通函数调用及少量已建模的 sklearn 对象。先支持一层辅助函数，再扩展到有限深度。每个样本至少含一条明确的训练与留出评估链。

核心变换为均值/标准差计算、标准化、固定值或统计值填充；特征选择作为对照，PCA 和词表学习为可选扩展。控制流先支持直线代码和简单分支。递归、动态导入、反射、未知全局可变状态等超过能力的部分应明确标记。

第一版不做时间序列泄漏、患者/用户分组泄漏、标签含义推断、重复使用测试集进行调参、Notebook 任意执行顺序、深度学习训练或全 Python 语义支持。训练集与评估集角色从调用和数据来源推导，不能只看变量名。评估集包括应与训练过程隔离的验证或测试数据，本研究不据此推断作者的完整模型选择意图。

## 3 问题定义与关键反例

本项目主任务的阳性定义是：留出评估样本的信息参与预处理统计量或状态计算，而该信息随后影响用于模型训练的表示，包括用训练和评估数据共同学习的状态转换训练数据。需要同时追踪样本来源、预处理状态来源和模型使用关系。发现调用 `fit`、发现操作在划分前发生，均不足以单独判断泄漏。

仅在测试集单独拟合变换、且不存在向训练过程回流的情况，不混入本项目主指标；可作为另外的评估协议问题讨论。预实验必须核对本定义与上游预处理输出的对应关系，遇到语义差异同时保留原输出和本任务的投影，不擅自修改基线来迎合标签。

以下为本项目设计的最小对照，假定 `X` 是行代表样本的二维数值矩阵，变换结果随后被划分并用于训练与评估：

```python
def center_columns(X):
    return X - X.mean(axis=0, keepdims=True)

def center_each_row(X):
    return X - X.mean(axis=1, keepdims=True)
```

前者使用跨样本统计量，先应用于完整数据再划分会形成所研究的泄漏；后者仅在各样本内部计算，在这些假设下不因“先变换后划分”而产生跨样本泄漏。若无法确定维度或样本轴，应返回未知，不能按名称猜测。NumPy 的轴语义见[官方 mean 文档](https://numpy.org/doc/stable/reference/generated/numpy.mean.html)。

另一个关键反例是仅在训练集拟合 scaler，再用同一状态转换训练和评估集：后者正常使用训练统计量，不能因为评估集调用了 `transform` 就报错。按样本独立处理的 Normalizer 也不等同于从所有样本学习统计量的 scaler，见[官方文档](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.Normalizer.html)。

填充策略需谨慎建模。直接 `fillna(0)` 与 `fillna(df.mean())` 是清楚的对照；`SimpleImputer(strategy="constant")` 的整体行为还受缺失指示列、空列处理和版本影响，不可一律视为无跨样本依赖。只有核查完整配置和数据形状相关行为后才能细化其效果，见[官方文档](https://scikit-learn.org/stable/modules/generated/sklearn.impute.SimpleImputer.html)。

不要求实际训练模型或观察分数升高后才判定泄漏。本项目比较的是代码中的依赖关系。小型人工样本可以执行来检查等价变换或实现错误，但运行输出不进入静态分析器，也不替代语义标注。

## 5 方法设计

采用“复用符号分析基础设施，增加自行设计的效果摘要层”的实现路径。保留原始基线独立运行；在派生实现中加入摘要选择、验证和调用点事实，使其重新进行符号推导。方法不能仅把基线告警交给 LLM 过滤，否则会被基线漏报限制。

处理流程为：源码与类型信息 → 提取候选函数和调用点 → 确定性效果推导或 LLM 提议 → 证据检查 → 调用点效果事实 → 符号传播 → 告警、路径和未知原因。

候选选择规则在开发集上冻结：选择可静态解析、位于训练/评估数据依赖链上的自定义预处理函数，以及效果可能受常量参数影响的预处理调用。不能根据测试集标签或“基线在此处出错”来选择候选。所有比较版本使用相同候选及同一份 API 原语规范。

### 5.1 摘要内容

摘要应使用固定 JSON Schema，至少包含：

- 函数/调用点标识、源码哈希和库版本。
- 参数到返回值、参数到对象状态的依赖边。
- 效果类别：`row_preserving`、`cross_row_reduce`、`fit_state`、`apply_state`、`unknown`。复杂函数可以包含多个效果，不能强行选一个总标签。
- 各效果所依赖的参数位置、接收者对象、样本轴和前置条件。
- 代码位置及可核查的 AST/原语证据；支持该效果的所有必要条件。
- 未解析调用、未知副作用和拒绝原因。

例如一个列均值中心化函数应指出“参数 0 经 axis=0 聚合，再影响返回值”；若均值计算存在但从未用于返回值或状态，不能仅凭其出现就判为跨样本输出依赖。LLM 只生成候选摘要，不输出最终真值标签。

### 5.2 核验边界

第一层检查格式、合法变量/参数、真实代码位置、源码哈希和调用点匹配。第二层使用确定性规则检查数据依赖、字面量参数、轴解释及对象状态关系；任何允许删除保守效果的摘要，必须有覆盖相关返回路径的规则推导。缺少完整证据的“各行独立”结论不能消除既有告警。

规则证明范围限制在已声明的 Python 子集和人工审查过的 API 原语上；动态形状、未知函数副作用和未覆盖分支不能由模型信心弥补。格式正确和代码位置正确不等于语义正确；报告不得声称系统对任意 Python 程序具有可靠性或完备性保证。核验可能很严格、甚至使 LLM 无额外收益，这也是有效实验结果。

### 5.3 与符号引擎的接入

先实现调用点级效果覆盖接口，再接模型。必须按调用位置、解析到的参数和必要上下文建模，不能把某次 `axis=1` 的判断应用到同一函数所有调用上。

派生实现可新增 `EffectAtCall`、摘要证据和覆盖许可等关系，再接入现有数据流规则；这些名称是待实现的设计，不是上游已存在的接口。不要把 JSON 拼接成任意 Datalog 规则或执行模型生成的代码。

增加跨样本依赖和细化保守效果应分开记录。细化仅针对核验覆盖的预处理效果，不能清除其他来源的数据依赖。`fit_state` 必须关联对象及状态版本；`apply_state` 必须关联实际使用的状态。最低版不支持复杂别名时，保留保守结果并记录限制。

核验失败时保留基线效果；当无法给出当前任务范围内的结论时，输出 `unknown`。结果状态区分 `leak`、`no_finding`、`unknown`、`error`、`timeout`。`no_finding` 仅表示该方法未报告所研究的问题，不是程序安全证明。

## 7 数据与标注设计

采用三个独立报告的部分，不能混合成一个看似很大的数据集。

| 部分 | 初始目标 | 用途 |
| --- | --- | --- |
| 受控基础样本 | 24 个独立样本家族，每家族一个泄漏版本和一个相应无泄漏版本，共 48 个程序 | 核心语义与误报/漏报评估 |
| 语义保持变体 | 对留出基础程序做变量重命名、1–2 层纯函数封装、无关注释变化 | 成对稳健性实验，不视为独立样本 |
| 原始真实 Notebook | 从作者公开材料中筛选约 20–30 个符合范围的程序，争取覆盖至少 3 个独立来源仓库；数量不足按实际报告 | 外部案例与局限分析 |

受控家族覆盖：完整数据统计后划分、只在训练集学习状态、按行变换、固定值填充、统计值填充、跨函数返回统计量、传入已拟合对象、无用统计计算、不同调用点参数、未知轴。扩展未获支持时不硬凑样本。

将 24 个家族按固定种子分为 8 个开发家族和 16 个测试家族；安全/泄漏配对及其所有变体必须留在同一分区。分区由预定生成规则决定，不按分析结果挑选。最终测试标签由评估器持有，提示开发不访问它们。AI 生成样本只能作为受控部分，不能称为自然发生的真实漏洞。

真实数据从给定文件清单按可解释的筛选规则处理：代码可解析、训练和评估关系可确定、任务在范围内、主要库可建模。按来源去重，无法确认来源仓库时用 Notebook 计数，不虚称多个真实项目。保留所有排除原因、失败和标签争议。若符合范围的程序不足 20 个，可使用较小的全部可用集合，或者按相同规则补充其他公开来源；不得按 N1 是否胜出筛选。

真实样本也要分开发和测试：初始总量中预留约 4–6 个用于预实验，其同源或近重复程序不得进入正式留出测试。其余作为冻结后的真实测试部分，单独报告开发数和测试数。优先按来源仓库分组；来源不完整时按可确认的 Notebook 家族去重，并说明独立性限制。不能一边阅读真实测试结果修改提示，一边将同批结果作为最终评估。

作者的 Notebook 级标签用于初筛和对照，不能自动当成精确调用点真值。标注每个预处理事件、统计量来源、训练/评估使用点、泄漏原因及库版本；对于 `N (due to overlaps)` 等非纯粹阴性、空白和无法解释的标签，先复核，再决定纳入、单独分析或排除。

将原始标注和本项目范围内的修订标注并存。学生至少复核全部最终正例、标签修订和争议项，并复核一个预先抽样的阴性子集；AI 可预整理证据，不能冒充独立人工标注者。若尚未人工复核，标注状态必须写为待复核。

静态分析输入只读取去标注代码，模型生成阶段不能访问原始作者 HTML、标签、目标测试结果、Notebook 输出或基线预测。源代码注释中含已有结论的情况要记录并去除；专门的误导注释实验另设输入版本，不改变标签。

## 8 指标和公平性

主指标以 Notebook/程序为单位：是否存在本研究范围内的预处理泄漏。报告 TP、FP、FN、TN、precision、recall、F1，以及每个方法的成功分析数、未知数、超时数和错误数。指标分母和零分母处理须写清楚，不能只报告一个 F1。

同时提供共同成功集合上的成对比较，以及完整预定样本集合上的覆盖率。对未知/错误不能按无泄漏处理：在完整样本上给出检测召回的保守结果（已知正例未检出即计为未检出），对精度等不能确定的量报告条件指标或上下界。不能悄悄删除导致某个版本失败的样本。

告警定位是次级指标，先统一为原始源码位置和训练/预处理事件，再去重。同一程序中的多条告警不能膨胀成多个独立程序。无法可靠映射的基线输出只参加程序级评估，并标出定位不可用。

摘要层单独报告效果分类错误、错误的安全摘要、核验接受/拒绝/回退数及人工核查结果。稳健性报告成对预测翻转率和正确率变化；需要同时检查所有变体都错误的“稳定”。家族或仓库为统计重采样单位，不把衍生变体当独立观测。样本较小时以描述性统计和案例为主，不强求显著性。

固定主模型和提示版本，主实验一次；在预先选定的 12 个测试家族中，各选一个程序做 3 次独立模型生成，报告重复一致性。温度为 0 也不声称绝对确定性。保存模型标识、服务版本信息（若可得）、参数、时间、输入/输出 token、缓存命中、延迟、错误及重试。

两类耗时分别报告：首次生成摘要的端到端成本、使用已保存摘要重放的成本。基线超时初设每程序 12 分钟，涵盖其多个内部阶段；在开发集确定后冻结。模型请求超时与总任务超时分别记录。

## 9 服务器实现顺序与验收

### 阶段 A 基线和资源探测

检查 Linux 架构、CPU/内存、磁盘、容器或 Conda/Micromamba、Node、网络与已配置模型端点。预设 CPU 分析和远程模型 API，不需要 GPU 训练。只记录模型配置，不输出密钥。

克隆并固定两个仓库及 Pyright 子模块。优先隔离重建上游环境，不依赖 `ubuntu:latest` 的可重复性；原始 Dockerfile 和部分 Python 包未固定版本，需要记录实际可用版本。基线优先保留 Python 3.8，项目的编排程序可以使用独立的新 Python 环境。

先运行基线 `test0.py` 至 `test4.py` 和至少一个函数封装样本，检查输出与已有断言。运行目录使用输入副本，因为上游会在输入旁边生成中间文件、清理事实目录；每个运行使用独立目录，防止旧结果污染和并发覆盖。

**验收：** 保存版本清单、构建步骤、完整日志、运行状态、可解析预处理输出和回归检查结果。退出码为 0 不是充分条件：上游部分失败通过文字或缺少产物表现，适配器必须验证各阶段和产物。

基线环境集中处理约一个工作日；超过约 8 小时仍未跑通时记录根因，尝试隔离版本或最小兼容补丁，不无限重写基线。无法解决则继续整理数据和离线模块，同时向学生报告阻塞；不能用自写工具冒充现有基线或自行改选题。

### 阶段 B 预实验与协议冻结

建立 6 对开发案例：列统计与行变换、完整数据与训练集拟合、固定值与均值填充、直接与封装调用、统计量返回、未使用的统计量。验证哪些问题由前端、类型信息、效果规则、状态传播或任务定义造成。

从真实 Notebook 中读取一小组候选，确认样本标注可映射和基线可执行。冻结候选规则、效果 Schema、支持范围、数据分区、指标和超时策略。记录学生对主要研究假设和范围的确认；不把尚未确认的决定写成学生已作出。

**验收：** 有一个完整预实验记录，至少两类明确的比较问题，并说明为什么需要或不需要 LLM。若基线已经处理所有开发案例，保留该事实，仍可研究摘要可靠性和相等性能，不人为削弱基线。

### 阶段 C 实现确定性接口

实现输入清理、位置映射、基线适配器、API 原语规范、调用点效果接口、S1 和统一结果格式。测试应覆盖实际语义错误：轴判断、拟合状态来源、不同调用点覆盖隔离、标签隔离、缓存失效和失败状态。避免只测试 JSON 能否读写。

**验收：** S0 可复现，S1 能处理范围内的正负对照；不同模式共享相同输入和前端。所有基线改动保留补丁，环境补丁与语义改动分开。

### 阶段 D 接入模型与核验

实现通用兼容端点客户端、结构化提示、Schema 检查、证据检查、缓存、重试与预算。缓存键含源码和依赖摘要、实际常量参数/上下文、库规范、模型及提示版本，不能只用函数名。

初始技术限额设为预实验累计 200,000 token、正式与重复实验合计再 1,000,000 token，输入输出均计入；只是软件上限，不是购买或付费授权。使用用户已有且许可的服务；未知计费或缺少凭据时继续离线工作，并请求资源信息。每请求最多 2 次重试，不因结果不理想反复抽样。离线 mock 仅用于接口测试，不能生成论文实验结果。

**验收：** N0/N1 复用同批摘要，错误摘要可解释地被接受、拒绝或回退；运行失败与模型成本真实可追溯。已有 API 原语规则也提供给 S1。

### 阶段 E 正式评估与报告

冻结代码、模型配置和分区后运行完整实验。保存全部失败，并在报告中讨论：收益来自规则还是模型、核验覆盖边界、自然样本与受控变体的差异、训练数据污染可能性、原论文标签与本项目定义的差异。

**验收：** 一条命令可以从保存的原始输出重建全部表格和图；另一条命令可重新运行分析。能仅凭公开仓库说明重现核心结果。完成至少 4 个代表性案例，覆盖真实成功、失败/漏报、误报或未知、核验作用；若某类未出现就如实说明，不编造。测试集上发现实现缺陷时保留修复前结果，记录修复原因并统一重跑所有受影响方法；不得把针对标签的调参称为一般修复。

样本与论文资源遵守各自许可。来源许可不清楚的 Notebook 不直接复制到公开仓库，可提供固定来源与下载/清理脚本。课程 PDF 仅用于本次私人交接，公开项目使用要求摘要与必要引用，不默认重新发布课程材料。

## 12 报告和最终完成标准

建议正文控制在约 8–9 页：摘要与引言约 1 页，问题与基线约 1 页，方法约 2 页，实验设置约 1 页，结果与案例约 2 页，局限、结论与 AI 使用约 1 页。根据实际结果调整，正文任何附录均计入页数。

报告主要表格为各方法的程序级结果与覆盖率、分案例类型的误报/漏报、摘要核验效果、稳定性与成本。主要图展示一条具体数据/状态依赖链及方法流程；数值全部由结果文件生成。

完成须同时满足：

1. 固定版本的现有符号基线成功运行，并有正负样本与日志证据。
2. 自行设计的方法实际调用模型产生摘要，再参与符号分析；只有实现阶段使用 AI 不满足这一点。
3. 对照版本共享输入和必要知识，N0/N1 共享原始摘要。
4. 数据分区、排除、标注及学生复核状态可追踪，最终结果没有标签或作者告警泄漏。
5. 实验包含已保存的真实运行结果，未知、超时和失败未被伪装成阴性。
6. 表图可由原始输出重建，复现说明经实际执行验证。
7. 英文报告满足格式、页数、个人信息、公开仓库链接和 AI Usage Statement 要求；占位符未填写时不能标记“可提交”。
8. 学生能解释方法、主要实验和至少一个失败案例，个人判断与 AI 帮助的记录真实。

## 13 给服务器的首轮任务

先完成阶段 A，再按阶段 B 建立预实验记录。首轮交付：环境检查、固定版本信息、基线试跑日志、正负结果表、数据材料解析摘要、初步范围及下一步。若阶段 A 顺利，继续开发，不需要为了报告常规进展而停工。

这一阶段不要训练模型、爬取大规模数据或先写带结果的论文。研究方法可依据预实验细化，但必须记录理由，保留原始基线与所有失败，不更改用户已选定的研究方向。
